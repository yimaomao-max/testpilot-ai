# Spec2Test AI 创业规划基线 V1.0

> 调研基准:2026-11-08。本文档是项目基线,后续 PRD、技术设计、数据库设计和开发任务均以它为依据。
> 前身:TestPilot AI(工作区 MVP 保留,作为技术验证底座逐步演进)。

## 1. 定位

**Spec2Test AI**(暂定名,启用前需核查域名/商标)—— From Requirements to Verified Playwright Tests。

把需求文档、用户故事和验收标准,转化为**可审核、可执行、可维护**的 Playwright 自动化测试。

不做"又一个 AI 用例生成器"(已是红海:TestSprite / Momentic / QA.tech / Functionize / Playwright 官方三 Agent)。

## 2. 目标用户(首发)

| 优先级 | 用户 | 痛点 |
|---|---|---|
| 最高 | 5–30 人 SaaS 团队 | 无专职 QA,回归成本高,已在用 GitHub/Playwright/CI |
| 高 | 初创技术团队、独立开发者 | 没时间写自动化测试 |
| 高 | QA 工程师 | 用例设计/脚本/失败定位耗时 |

首发市场:美国/英国/加拿大/澳大利亚等英语市场;国内第二阶段。

## 3. 三个差异化能力(核心竞争力)

1. **Requirement Traceability 需求追溯**
   `Requirement → Acceptance Criteria → Test Case → Playwright Test → Test Run → Failure Analysis`
   回答:这条测试对应哪个需求?哪个验收标准没覆盖?需求改了哪些测试要重生成?
2. **Evidence-based Failure Analysis 基于证据的失败分析**
   失败分类(产品缺陷 / 元素变化 / 脚本错误 / 环境问题 / 数据问题),每条结论附证据:截图、Trace、控制台、网络错误、预期 vs 实际。AI 只给带置信度的判断,不冒充确定根因。
3. **Portable Playwright Code 可移植代码**
   输出标准 TypeScript `.spec.ts`,可导出到用户 Git 仓库自维护,不锁平台。

## 5. 产品形态

```
Chrome Extension(录制/选元素/Locator 建议)  →  Web SaaS(需求→用例→代码→报告, AI 中枢)  →  Local Runner / CLI(本地执行, Trace 上传)
```

不自研浏览器自动化引擎;用户代码优先本地执行。

## 7. 90 天执行计划

| 阶段 | 天数 | 交付 | 验收 |
|---|---|---|---|
| 市场验证 | 1–10 | 20 人访谈、10 份真实需求、原型 | 5 试用意愿、2–3 付费承诺 |
| 需求→用例 | 11–25 | 登录/项目、需求解析、验收标准、用例生成与审核 | 10 份真实需求可生成可审核用例 |
| Playwright 生成 | 26–40 | TS 代码生成、Locator、导出、Runner 原型 | 生成的测试能在真实项目运行 |
| 插件+报告 | 41–55 | 插件录制、本地执行、截图/Trace、报告 | 需求→真实执行走通 |
| 失败分析 | 56–70 | 失败分类、证据、追溯、额度 | 区分≥4 类失败原因并附证据 |
| 发布验证 | 71–90 | Stripe、官网、插件商店、PH 发布 | 50–100 激活、5–10 付费 |

## 8. 预算与核心指标

- 初期现金:$30–130/月
- 工作量:约 44–69 工作日(8–12 周,按 4–6h/天)
- 核心指标:首次生成 ≤5 分钟;用例可审核率 ≥80%;脚本首次可执行率 ≥70%;20 访谈/10 需求样本/5–10 付费

## 9. 三个不要

1. 不自研浏览器自动化引擎(用 Playwright)。
2. 不把"AI 生成用例"当唯一卖点(必须绑定追溯+执行+证据)。
3. 第一版不做完整测试管理平台(不做 Selenium/Cypress/Appium/移动端)。

## 10. V1 边界

**做**:注册登录、项目管理、需求输入、AI 解析/验收标准/用例生成、用例审核编辑、Playwright TS 生成、插件基础录制、Locator、Local Runner、执行报告、截图 Trace、AI 失败分类、代码导出、基础订阅额度。

**不做**:完整测试管理平台、多框架、移动端、企业权限/私有化、Jira 双向同步、云端浏览器集群、全自动无人审核修复。

## 11. V1 暂不实现之外的长线路线

GitHub PR(P1)→ Jira(P1)→ 自动修复(P1)→ 协作/权限(P2)→ API/MCP 接入 AI 编程工具(P2)。

> 长期愿景:成为 AI 编程工作流中的**质量验证层**(这次改动影响哪些需求?该跑哪些测试?失败说明什么?)。
